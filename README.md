# Visual Company

บริษัทจำลอง pixel art (สไตล์ GBA gen 3) ที่พนักงานทุกคนเป็น AI agent
จ้างพนักงานเข้ามา -> ถามคำถาม -> ทีมที่เกี่ยวข้องเดินเข้าห้องประชุม ถกกัน 2 รอบ
แล้วหัวหน้าทีมเดินมารายงานที่โต๊ะคุณ

## เริ่มใช้งาน

```bash
npm install
npm run dev
```

เปิด http://localhost:3210 แล้วกดปุ่ม **คีย์ของฉัน** บนแถบบน ใส่คีย์ Claude หรือ Gemini
ไม่ใส่ก็รันได้ - จะเข้าโหมดสาธิต animation ครบแต่คำตอบเป็นข้อความตัวอย่าง

> พอร์ตถูกล็อกไว้ที่ **3210** ใน `package.json` ตั้งใจไม่ใช้ 3000 เพราะโปรเจกต์ Next อื่น
> มักจองไว้แล้ว ถ้าปล่อยให้ Next เลือกเอง มันจะเลื่อนไป 3001 หรือ 3002 เงียบ ๆ
> แล้วเปิด localhost:3000 จะไปเจอโปรเจกต์อื่นแทน
> ถ้า 3210 ชนกับอะไรอยู่ จะขึ้น `EADDRINUSE` ตรง ๆ แก้โดยเปลี่ยนเลขใน script `dev`

## เลือกผู้ให้บริการ / ใส่คีย์

รองรับ 2 เจ้า สลับได้จากในหน้าเว็บ

| | โมเดลดีฟอลต์ | เอาคีย์จาก | หมายเหตุ |
|---|---|---|---|
| **Claude** | `claude-opus-5` | Anthropic Console -> API keys | ต้องมีเครดิตในบัญชี - **subscription Max/Pro ใช้กับ API ไม่ได้** เป็นคนละกระเป๋ากัน |
| **Gemini** | `gemini-3.7-flash` | Google AI Studio -> Get API key | มี free tier แต่จำกัดจำนวนเรียกต่อนาที/ต่อวัน |

ในแผงคีย์มีปุ่ม **ตรวจคีย์ + โหลดรายชื่อโมเดล** - ดึงรายชื่อโมเดลที่คีย์นั้นเรียกได้จริง
(`client.models.list()` ของ Anthropic / `ai.models.list({config:{queryBase:true}})` ของ Gemini)
แล้วเปลี่ยนช่องโมเดลเป็น dropdown จะได้ไม่ต้องเดาชื่อ และเป็นตัวตรวจคีย์ไปในตัว
เพราะคีย์ผิดจะ error ตรงนี้เลยโดยไม่เสียเครดิต - endpoint นี้ไม่คิดเงิน

ใส่คีย์ได้ 2 ทาง:

1. **ในหน้าเว็บ (BYOK)** - ปุ่ม คีย์เก็บใน `localStorage` ของเบราว์เซอร์เท่านั้น
   ส่งไปที่ API route ของแอปทาง HTTP header (ไม่ใช่ body จะได้ไม่ติดไปกับ log)
   ใช้เฉพาะภายในคำขอนั้น ไม่เขียนลงดิสก์ ไม่ส่งกลับมาที่ client
   เหมาะกับตอนให้คนอื่นมาลองเล่นด้วยคีย์ของเขาเอง
2. **ในไฟล์ `.env.local`** - คัดลอกจาก `.env.example` (คีย์จากหน้าเว็บจะถูกใช้ก่อนเสมอ)

`ask()` ใน `src/lib/llm.ts` เป็นจุดเดียวที่แตะ LLM - ที่เหลือทั้งระบบ (บทบาท, 2 รอบถก,
SSE, animation) เป็น prompt กับ orchestration ล้วน ไม่ผูกกับผู้ให้บริการ
เพิ่มเจ้าที่สามก็เขียนอะแดปเตอร์ตัวเดียวจบ

> **หมายเหตุเรื่อง SDK ของ Gemini** - โค้ดนี้ใช้ `ai.models.generateContent()` ไม่ใช่
> `ai.interactions.create()` ที่เอกสารใหม่แนะนำ เพราะ `interactions` รองรับเฉพาะโมเดลรุ่นใหม่:
> เลือก `gemini-2.5-*` จาก dropdown แล้วจะโดน 404 ทั้งที่โมเดลมีอยู่จริงในบัญชี
> `generateContent` รองรับข้ามรุ่นได้กว้างกว่า และคืนรายละเอียด error ดีกว่าด้วย
>
> `thinking_level` เป็นของรุ่น 3 ขึ้นไป - โค้ดจะส่ง `thinkingConfig.thinkingLevel` เฉพาะเมื่อชื่อโมเดล
> เป็นรุ่น 3+ และมี fallback ถอดออกถ้าโมเดลไม่รับ

## Supabase - Sign In + Create My Office (ไม่ใส่ก็รันได้)

ไม่ตั้งค่า = แอปทำงานแบบ **ในเครื่องอย่างเดียว** (จ้างพนักงานแล้วรีเฟรชหาย) เหมือนเดิมทุกอย่าง

เปิดใช้:

1. สร้างโปรเจกต์ที่ [supabase.com](https://supabase.com)
2. เอา [`supabase/schema.sql`](supabase/schema.sql) ไปวางใน **SQL Editor** แล้ว Run (รันซ้ำได้ ไม่พัง)
3. คัด `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` จาก Project Settings -> API ใส่ `.env.local`
4. รีสตาร์ท dev server -> กดปุ่ม บนแถบบน -> สมัคร/เข้าสู่ระบบ -> สร้างออฟฟิศ

> ตอนทดสอบให้ปิด **Confirm email** ที่ Authentication -> Providers -> Email ไม่งั้นต้องยืนยันอีเมลก่อนถึงจะเข้าได้

**anon key ไม่ใช่ความลับ** - ขึ้นต้นด้วย `NEXT_PUBLIC_` ให้เบราว์เซอร์เห็นได้ถูกต้องแล้ว
ความปลอดภัยอยู่ที่ **RLS ใน Postgres** ไม่ใช่ที่โค้ดฝั่ง client
(**ห้ามเอา `service_role` key มาใส่เด็ดขาด** - มันข้าม RLS ได้ทั้งหมด)

| ตาราง | เก็บอะไร |
|---|---|
| `office` | ออฟฟิศ + เจ้าของ |
| `office_member` | ใครอยู่ออฟฟิศไหน (owner / exec / viewer) |
| `employee` | พนักงานที่จ้าง - ชื่อ บทบาท สี ที่นั่ง |

RLS มีกฎเดียวซ้ำทุกตาราง: *แตะได้เฉพาะ row ของออฟฟิศที่ตัวเองเป็นสมาชิก* บังคับที่ DB
บั๊กใน API ก็ทำข้อมูลข้ามออฟฟิศไม่ได้ ฟังก์ชัน `is_office_member()` เป็น `security definer`
เพื่อกัน policy เรียกตัวเองวนไม่จบ

### เตรียมไว้สำหรับ sync ตำแหน่ง (เฟสถัดไป)

ทุก avatar มีฟิลด์ `owner: 'sim' | 'remote'` และ `World` มี `applyRemoteState(id, {px,py,dir,pose})`
อยู่แล้ว - เฟสนี้ยังไม่มีใครเรียก พอถึงเฟส realtime งานที่เหลือคือ *เอา channel มาป้อนตรงนี้*
ไม่ต้องรื้อ update loop

**agent ไม่ต้อง sync พิกัด** เพราะ pathfinding เป็น BFS บนกริด static -
`findPath(จาก,ถึง)` คืนเส้นทางเดียวกันทุกเครื่อง broadcast แค่ *"ต้นเดินไปที่นั่ง (18,2)"* ก็พอ
มีแต่ avatar ของคนจริงที่ต้องส่งพิกัดจริง ซึ่งมีไม่กี่คน

## แนวคิด

### จ้างพนักงาน = spawn agent ที่เรียน skill มาก่อน

แต่ละแผนกผูกกับไฟล์ `skills/<แผนก>.md` ตอนถูกเรียกใช้ เนื้อไฟล์นั้นจะกลายเป็น
system prompt ของ agent ทุกตัวในแผนก

เพิ่มแผนกใหม่ = เพิ่ม 1 entry ใน `DEPARTMENTS` + 1 ไฟล์ใน `skills/`

### ทำยังไงให้ agent จากโมเดลเดียวกัน "เห็นต่างจริง"

นี่คือปัญหาหลักของ multi-agent debate - โมเดลเดียวกัน + prompt คล้ายกัน = คำตอบคล้ายกัน
และ Opus 5 ไม่รับ `temperature`/`top_p` ด้วย เอาความหลากหลายจากการสุ่มไม่ได้เลย
ความต่างจึงต้องมาจากโครงสร้าง prompt ล้วน ๆ โปรเจกต์นี้ใช้ 3 กลไก:

**1. บทบาทที่ขัดกันโดยโครงสร้าง ไม่ใช่บุคลิก** (`ROLES` ใน `src/lib/departments.ts`)

| ลำดับที่จ้าง | บทบาท | หน้าที่ | ข้อห้าม |
|---|---|---|---|
| 1 | ผู้เสนอ | หาทางที่เดินหน้าได้ | **ห้ามสรุปว่า "อย่าทำ"** |
| 2 | ผู้ค้าน | หาว่าข้อเสนอจะพังตรงไหน | **ห้ามลงท้ายว่าเห็นด้วย** |
| 3 | ผู้ตรวจสอบ | แยกข้อเท็จจริงจากสมมติฐาน | ไม่เข้าข้างใคร |
| 4 | ⏱️ ผู้ดูความเป็นไปได้ | ประเมินคน เวลา เงิน | - |

ข้อห้ามสองข้อแรกคือหัวใจ - มันบังคับให้ผู้เสนอกับผู้ค้านเดินไปคนละจุดหมาย
**ตั้งแต่รอบแรกที่ยังไม่เห็นหน้ากัน** และแต่ละบทบาทถูกบอกเกณฑ์ประเมินคนละแบบ

**2. มุมมองเฉพาะแผนก** (`lenses`) - บทบาทเดียวกันในคนละแผนกจะมองคนละเรื่อง
ผู้ค้านฝ่ายกฎหมายมองความเสี่ยงถูกฟ้อง ผู้ค้านฝ่ายวิศวกรรมมอง failure mode ตอนโหลดสูง

**3. กันการยอมกันในรอบ 2** - LLM มีแนวโน้ม sycophantic สูงมาก อ่านความเห็นเพื่อนแล้ว
เห็นด้วยหมด รอบ 2 จึงบังคับรูปแบบ `ค้าน: / ตกหล่น: / จุดยืน:` โดย
- ห้ามเขียน "เห็นด้วยกับทุกคน" หรือ "ไม่มีข้อค้าน"
- ถ้าจะเปลี่ยนใจ ต้องระบุ **หลักฐาน** ที่ทำให้เปลี่ยน - "ฟังดูมีเหตุผล" ไม่นับ
- ห้ามค้านลอย ๆ ที่ใช้ได้กับทุกเรื่อง

**ตรวจได้ว่าถกจริงไหม** - แชทจะโชว์ป้าย `ค้านกัน N ข้อ` จากการนับบรรทัด `ค้าน:`
ที่มีเนื้อจริงในรอบ 2 ถ้าขึ้น "ไม่มีใครค้าน" บ่อย ๆ แปลว่า prompt ยังคุมโมเดลไม่อยู่
ให้ไปแก้ `ROLES[*].round2` ใน `departments.ts`

**คนสรุปไม่ใช่คนถก** - รอบสรุปเป็นบทบาท "ประธาน" ที่ถูกสั่งให้ **ตัดสิน** ว่าฝั่งไหน
มีน้ำหนักกว่า และ **ห้ามเกลี่ยให้ทุกคนถูก** (การเกลี่ยคือวิธีที่คำตอบกลายเป็นน้ำ)
คนที่เดินมารายงานคือผู้ตรวจสอบ - ตัวกลางที่ไม่ได้เชียร์ข้อเสนอของตัวเอง

### วงจรการถกกัน (`src/app/api/ask/route.ts`)

| รอบ | ทำอะไร | effort |
|---|---|---|
| 1 | แต่ละบทบาทตอบจากหน้าที่ตัวเอง ยังไม่เห็นของเพื่อน (ขนานกัน) | `low` (ผู้ค้าน `medium`) |
| 2 | อ่านของเพื่อนแล้ว **บังคับให้ค้าน** (ขนานกัน) | `low` (ผู้ค้าน `medium`) |
| สรุป | ประธานตัดสินว่าฝั่งไหนมีน้ำหนักกว่า | `medium` |

ผู้ค้านใช้ effort สูงกว่าเพราะการหาช่องโหว่ที่ตรงจุดต้องคิดลึกกว่าการเสนอ

รวม 7 คอลต่อ 1 คำถาม (3 + 3 + 1) สตรีมกลับมาเป็น SSE ทีละ event
หน้าเว็บจึงขยับ animation ตามจังหวะจริงของการถกได้ ไม่ใช่หน่วงเวลาหลอก

โมเดลดีฟอลต์คือ `claude-opus-5` (thinking เปิดอยู่โดยดีฟอลต์ `max_tokens` จึงเผื่อไว้
เพราะมันคุมทั้ง thinking และข้อความตอบ) เปิด server-side fallback ไว้ด้วย เผื่อ
classifier ปฏิเสธคำถามจะได้มีโมเดลสำรองรับช่วงในคอลเดียวกัน

### Animation ผูกกับงานจริง

**ผู้บริหาร (ตัวคุณ) มีห้องทำงานของตัวเองที่มุมล่างซ้าย** (cols 1-3, rows 13-14 ประตูที่ (4,13))
ตอนไม่มีประชุมจะนั่งทำงานอยู่ในห้อง พอมีวาระถึงเดินออกมานั่งหัวโต๊ะประชุม
ประชุมจบก็เดินกลับห้อง - บทสรุปจึงจบคาห้องประชุม ไม่มีใครต้องเดินไปหาใคร

```
ผู้ใช้ถาม
  -> saveView() + focusRect(MEETING_RECT)   กล้องซูมเข้าห้องประชุมเอง
  -> gather(ids)              ทีมเดินเข้าห้อง + บอสเดินออกจากห้องตัวเอง
                             มานั่งหัวโต๊ะ (await จนนั่งครบทุกคน)
  -> boss พูด "📋 วาระวันนี้: <คำถาม>"      เปิดประชุมด้วยคำถามของคุณเอง
  -> SSE opinion มาถึง        พักไว้จนครบรอบ แล้วเข้าคิวตามลำดับบทบาท
                             (ผู้เสนอ -> ผู้ค้าน -> ผู้ตรวจสอบ) ทีละคน
  -> รอบ 2 ค้านใคร            คนพูดหันไปหาคนนั้น + คนนั้นขึ้นไอคอน ❓
  -> waitForSpeech()          รอถกจบก่อน ไม่ให้บทสรุปทับบทสนทนา
  -> หัวหน้าทีมหันไปหาบอส แล้วพูดบรรทัดสรุป -> บอสพยักหน้า 💡
  -> ข้อความเต็มโผล่ในแชท
  -> disperse() + restoreView()             ทีมกลับโต๊ะ บอสกลับห้องตัวเอง
                                           กล้องกลับมุมเดิม
```

**คิวคำพูด** เป็นหัวใจของจังหวะการสนทนา - พูดทีละคน เว้นจังหวะ 0.5 วิ และ
**ถือคิวไว้ถ้าคนพูดยังเดินอยู่** (ไม่งั้นจะกลายเป็นเดินไปพูดไป) คิวไม่ตัดทิ้ง
ทุกคนต้องได้พูดครบ การประชุมจึงยาวเท่าที่บทสนทนายาวจริง
ไอคอนสุ่มระหว่างรอ LLM จะเงียบทันทีที่เริ่มมีคนพูดจริง

**ฟองคำพูดข้อความจริง** วาดบนเลเยอร์จอ (ไม่ใช่ base canvas 16px) เพราะข้อความไทย
ที่ความละเอียดนั้นอ่านไม่ออก ตัวอักษรทยอยโผล่ ~42 ตัว/วินาทีเหมือนกำลังพูด
ตัดบรรทัดทีละตัวอักษรเพราะภาษาไทยไม่มีช่องว่างระหว่างคำ และมีระบบกันฟองซ้อนกัน:
คนที่อยู่ครึ่งบนของจอฟองจะห้อยลงล่าง (ไม่งั้นตอนนั่งเรียงกัน 3 คนฟองจะถูกดันหลุดขอบบน)
ในฟองมีชื่อ+บทบาทกำกับ จะได้รู้ว่าใครพูดตอนซ้อนกันหลายฟอง

รอบ 2 ฟองจะโชว์เฉพาะบรรทัด `ค้าน:` เพราะนั่นคือส่วนที่น่าดูที่สุดของการถก

ปิดกล้องอัตโนมัติได้ที่ปุ่ม 🎥 บนแถบบน - และแค่ลาก/ซูมเองระหว่างประชุม
กล้องอัตโนมัติจะถอยให้ทันที ไม่แย่งกับผู้ใช้

ตอนว่าง agent จะสุ่มพฤติกรรมเอง: นั่งทำงาน ชงกาแฟ กินข้าว นั่งโซฟา
ออกไปนั่งม้านั่งในสวน ยืนดูบ่อน้ำ หรือเดินไปคุยกับเพื่อน (`World.decide()`)

## ดีบัก

ตอน dev จะมี `window.vcWorld` ให้เรียกจากคอนโซล เช่น

```js
vcWorld.debugStep(10)          // เดินเวลาจำลอง 10 วินาทีทันที (ไม่ต้องรอ rAF)
vcWorld.say(vcWorld.employees[0].id, 'ทดสอบฟองคำพูด', 30)
vcWorld.focusRect({x:256,y:16,w:112,h:96})   // ซูมเข้าห้องประชุม
```

`debugStep` มีประโยชน์เวลาเบราว์เซอร์ throttle `requestAnimationFrame` (เช่นตอนแท็บไม่ active
จะเหลือ ~1fps ทำให้ตัวละครเดินช้ามากจนดูเหมือนค้าง)

## ข้อจำกัดตอนนี้

- โต๊ะมี 12 ที่ จ้างได้สูงสุด 12 คน
- ถามได้ทีละคำถาม (ระหว่างประชุมปุ่มถามจะถูกล็อก)
- ทีมจำกัดที่ 3 คนต่อการประชุม แม้จ้างไว้มากกว่านั้น
- agent ยังไม่มีความจำข้ามคำถาม แต่ละครั้งเริ่มใหม่
- ยังไม่มีการประชุมข้ามแผนก (ถามได้ทีละแผนก)
- ต้นทุนประมาณ **$0.25-0.35 ต่อคำถาม** (7 คอล, output คือ ~75% ของค่าใช้จ่าย)
  ยังไม่เคยวัดกับคีย์จริง - ตัวเลขนี้เป็นการประมาณจากความยาว prompt/คำตอบ
